## 1. 주요 채용 사이트별 접근 방법

### 사람인 (Saramin) - 공식 API 제공 (권장)

| 항목 | 내용 |
|------|------|
| API URL | `https://oapi.saramin.co.kr/job-search` |
| 인증 | access-key 발급 필요 (앱 등록 후 승인) |
| 호출 제한 | 1일 최대 500회 |
| 응답 형식 | JSON / XML |
| 주요 필드 | 회사명, 직무, 경력, 학력, 연봉, 지역, 마감일, 공고 URL |

**장점**: 합법적, 안정적, 구조화된 데이터
**단점**: 승인 필요, 일 500회 제한, 공고 상세 내용(자격요건 등)은 미포함될 수 있음

### 잡코리아 (JobKorea) - API 제한적, 크롤링 주의

| 항목 | 내용 |
|------|------|
| API | 공공기관/학교 대상 우선 제공 (일반 개발자 접근 어려움) |
| URL 패턴 | `https://www.jobkorea.co.kr/Recruit/GI_Read/{공고ID}` |
| robots.txt | AI/LLM 크롤러 차단, 일반 크롤러는 채용정보 페이지 부분 허용 |
| 기술 스택 | SSR 기반, 정적 HTML 파싱 가능 |

### 원티드 (Wanted) - 동적 페이지, 크롤링 난이도 높음

| 항목 | 내용 |
|------|------|
| URL 패턴 | `https://www.wanted.co.kr/wd/{공고ID}` |
| 페이지 유형 | SPA (React 기반), 동적 렌더링 |
| 필요 도구 | Playwright / Selenium (헤드리스 브라우저 필수) |

### 캐치 (CATCH)

| 항목 | 내용 |
|------|------|
| URL 패턴 | `https://www.catch.co.kr/Comp/RecruitInfo/{회사코드}` |
| robots.txt | API 엔드포인트 차단, 일반 페이지 허용 |

## 2. URL 기반 범용 파서 아키텍처

```
[사용자 URL 입력] → [URL 도메인 판별] → [사이트별 파서 선택] → [데이터 추출] → [AI 정규화]
```

### 방법 1: 정적 HTML 파싱 (Cheerio)

- **적합 대상**: 잡코리아, 캐치 (SSR 기반)
- **장점**: 빠름, 의존성 적음, 서버리스에서 실행 가능
- **한계**: 동적 렌더링 페이지(원티드 등) 불가

### 방법 2: 헤드리스 브라우저 (Playwright)

- **적합 대상**: 원티드 (SPA)
- **장점**: 모든 동적 사이트 대응 가능
- **한계**: 리소스 소모 큼, Vercel 서버리스에서 실행 어려움 (Koyeb에서 실행 권장)

### 방법 3: AI 기반 범용 파싱 (가장 유연)

- HTML을 LLM에 직접 전달하여 구조화
- **장점**: 사이트 구조 변경에 강건함, 유지보수 비용 낮음
- **한계**: API 비용 발생, 속도 느림

### 권장 전략: 하이브리드 접근

1. **사람인**: 공식 API 사용 (1순위)
2. **잡코리아/캐치**: Cheerio 정적 파싱
3. **원티드**: Koyeb 백엔드에서 Playwright 실행
4. **기타**: AI 기반 범용 파싱 (fallback)

## 3. 법적 이슈

### 핵심 판례

- **잡코리아 vs 사람인 (2016)**: 경쟁 관계에서의 상업적 크롤링은 부정경쟁행위
- **대법원 2022도1533**: 접근 권한을 초과한 크롤링은 정보통신망법 위반 가능

### 법적 리스크 최소화 전략

| 방법 | 리스크 |
|------|--------|
| 공식 API 사용 | 거의 없음 |
| robots.txt 준수 크롤링 | 낮음 |
| 사용자가 직접 URL 입력 | 낮음 |
| 대량 자동 크롤링 | 높음 |
| 경쟁 서비스 데이터 복제 | 매우 높음 |

### 권장 접근법

```
[사용자가 채용공고 URL을 직접 입력]
  → [해당 URL 1건만 fetch하여 파싱]
  → [수집된 원문은 저장하지 않음, 분석 결과만 저장]
```
